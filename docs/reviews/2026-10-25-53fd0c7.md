## Findings

### F1 (major) A participant action added in a later `taskGraph.whenReady` still runs after the success record

- **What:** D-097 moves `RecordSuccess` into the plugin's `taskGraph.whenReady` callback (`GitMavenPublisherPlugin.java:107-119`) and states that
  "actions that build scripts and other plugins add to a participant while configuring ... were all added before the graph is ready".
  That is not so: `whenReady` callbacks run in registration order, and the plugin registers its callback when it is applied. Any
  `whenReady` callback registered later (a subproject build script after `subprojects { apply plugin }`, a plugin applied after this one,
  a project evaluated after the one that applied the plugin) is still configuration time and appends its `doLast` after the record.
  When that action fails, the participant is FAILED, but already recorded, and the finalizer `gitPublisherPush` pushes.
  Design section 2 (Gradle, D-033): "A failed publication prevents push." D-097's stated limit names only actions added during execution.
- **Evidence:** `gradle-plugin/src/test/java/io/github/ivangsa/gitpublisher/gradle/review/R32LateWhenReadyActionReviewTest.java`, b's build script:
  ```groovy
  def participant = tasks.named('publishMavenPublicationToGitPublisherRepository')
  gradle.taskGraph.whenReady { participant.get().doLast { throw new GradleException('late boom in b') } }
  ```
  Fails for the default schedule, `--continue` and `--configuration-cache` (entry stored, no problems reported): output shows
  `> Task :b:publishMavenPublicationToGitPublisherRepository FAILED` and `git-maven-publisher: pushed <sha> after 1 attempt(s)`; the branch has a commit.
- **Side note:** every project that applies the plugin registers its own `whenReady` and adds a `RecordSuccess` to every participant of the
  graph, so with N projects each participant carries N record actions; the first one already records. Any fix that relies on "the record is
  the last action" must account for that.
- **Impact:** same class of defect as F1 of the previous review, through a narrower but ordinary configuration hook: a build that failed in a
  participant publishes.
- **Suggested task:** R32. Make the record fail closed: for example, `RecordSuccess` records only when it is the last action of the task
  (check `task.getActions()` at execution time, one record action per participant), so a later action leaves the participant unrecorded
  and D-098 refuses the push with a failed build; or another mechanism that sees the task's final outcome before the finalizer runs.
  Keep the configuration cache. Correct the D-097 claim in decisions. Restore T36 and R26.
