## Findings

### Major

**F1. A 403 on push is retried; the auth check also matches words in the repository URL.**
- What: `GitPublication.isFatal` classifies by substrings of the JGit message ("unauthorized", "forbidden", " 403", ...).
  JGit reports an HTTP 403 as `<url>: git-receive-pack not permitted on '<url>/'` (`JGitText.serviceNotPermitted`), which
  matches none of them. A 403 is GitHub's answer to a token without `Contents: write` (`GITHUB_TOKEN` without
  `contents: write`, a read-only PAT), the most likely auth failure in practice. The message also contains the URL,
  so any transport error on a repository named for example `authentication-snapshots` is treated as fatal.
- Evidence: `src/test/java/io/github/ivangsa/gitpublisher/review/R15AuthFailureClassificationTest.java`, run against a real
  `GitServlet` with `http.receivepack=false`:
  `aForbiddenPushFromARealGitServerIsAnAuthenticationFailure` (message `http://127.0.0.1:.../remote.git: git-receive-pack
  not permitted on '...'`, `isFatal` false), `aForbiddenPushMakesExactlyOneAttempt` (expected 1, was 5),
  `aTransportErrorIsRetriedWhateverTheRepositoryIsCalled` (`.../acme/authentication-snapshots.git: 503 Service Unavailable`,
  `isFatal` true). `GitPublication.java` `isFatal`.
- Why it got through: `GitPublisherRetryTest.jgitFailure` asserts `isFatal == (status == 401 || status == 403)`, but no test
  calls it with 403; the 401 is captured from `ls-remote` against a plain servlet, not from a push to a Git server.
- Impact: design §4 3.vi ("Auth failure → fail fast") and T21's "an auth failure makes exactly one attempt" do not hold for 403;
  the user waits through the whole budget and gets "transport error". The URL match turns a retryable outage into a hard failure.
- Suggested task: R15. Classify on the HTTP status / JGit message key (`notAuthorized`, `serviceNotPermitted`,
  `authenticationNotSupported`, no-CredentialsProvider) without looking at the URL part of the message; cover 401 and 403 from
  a real `GitServlet`.

### Minor

**F2. A push the remote refuses for good is retried as a "transport error".**
- What: `GitRemote.push` turns every branch status other than OK/UP_TO_DATE/REJECTED_REMOTE_CHANGED into an `IOException`;
  the loop retries it `maxAttempts` times and reports `transport error: ... REJECTED_OTHER_REASON (non-fast forward)`.
  A protected branch, a pre-receive hook or a file size limit is a permanent refusal, not a transport error (design §4 3.vi
  retries lease failures and transport `IOException`s only).
- Evidence: `src/test/java/io/github/ivangsa/gitpublisher/review/R16PermanentPushRejectionTest.java` (real JGit receive-pack,
  `receive.denyNonFastForwards=true`): message `after 5 attempts: transport error: the remote rejected the push to
  refs/heads/gh-pages: REJECTED_OTHER_REASON (non-fast forward)`, 4 retry warnings.
- Impact: slow failure (up to the whole back-off budget) with a misleading diagnostic; nothing wrong is pushed.
- Suggested task: R16. Treat a remote rejection of the branch update (any status other than OK, UP_TO_DATE,
  REJECTED_REMOTE_CHANGED) as fatal with the remote's message, and say in the message that the branch must allow force pushes;
  record in design §4 and decisions.

**F3. The token is not cleared on `close()`.**
- What: design §8 "Token held as char[], wrapped in UsernamePasswordCredentialsProvider per operation, cleared on close()".
  `GitPublication.close()` only closes the object store; `GitRemote` never calls `UsernamePasswordCredentialsProvider.clear()`
  on its copies.
- Evidence: `src/test/java/io/github/ivangsa/gitpublisher/review/R17TokenClearedOnCloseTest.java`: after `Publication.close()`
  the token still reads `s3cr3t`.
- Impact: the token outlives the publication in memory; a silent divergence from design §8.
- Suggested task: R17. Clear the providers after each operation and the `Token` on `Publication.close()` (or change design §8 to
  name the owner that clears it, with a decision; then this test is provably wrong and is updated with it).

**F4. A failed publication still uploads its tree and moves `refs/publisher/tree` on the remote.**
- What: the branch (with lease) and the lease-free tree hint go in one non-atomic `Transport.push`. When the lease rejects the
  branch, JGit still sends the pack and force-moves `refs/publisher/tree` to the failed publication's tree. After a conflict,
  the remote holds the conflicting tree under a ref while the message says "nothing was pushed" (design §7: "Nothing partial
  is ever pushed").
- Evidence: `src/test/java/io/github/ivangsa/gitpublisher/review/R18FailedPublicationMovesNoRefTest.java`: after the conflict,
  `refs/publisher/tree` is `341d8fc...` (A's tree), not `f57b021...` (the tree of the branch tip).
- Impact: not served (the branch is intact), but the remote stores and references content of a publication that failed,
  and the diagnostic is false. D-020/D-027 did not consider the rejected-branch case.
- Suggested task: R18. Move the hint only after the branch update succeeded (for example a second push of the tree ref after
  OK, status ignored, or JGit atomic push where supported), or amend design §4/§7 and D-027 to accept it and reword the message.
