## Findings

### F1 (minor): `+` stays literal, so an S3-hosted release repository is asked for another key and released snapshots are never cleaned

- **What:** D-114 leaves `, = : @ ! $ & ' ( ) * +` literal and says that no common server gives them a path meaning
  ("Tomcat/Jetty/nginx/Apache/Pages/CDNs treat only `;` specially"). That is wrong for `+` on Amazon S3. S3 (REST and
  website endpoints, and CloudFront in front of them, a common way to host a Maven release repository) decodes a literal
  `+` in the request path as a space. Only `%2B` names a key that contains `+`. `ReleaseCheck.encode`
  (`core/src/main/java/io/github/ivangsa/gitpublisher/ReleaseCheck.java:81-98`) sends `1.0+build` unchanged. The check
  therefore asks for the key `.../1.0 build/lib-1.0 build.pom`, gets 404, and keeps `1.0+build-SNAPSHOT` forever even
  after `1.0+build` has been released. `+` is common in versions: semver build metadata, sbt-dynver.
- **Evidence:** a probe of `encode` (reflection on the built class) gives `1.0+build -> 1.0+build` and `1.0;rc -> 1.0%3Brc`.
  The new failing review test
  `core/src/test/java/io/github/ivangsa/gitpublisher/review/R48ReleaseCheckPlusSignReviewTest.java` uses a JDK
  `HttpServer` that applies the S3 rule: the raw path is form-decoded, so `+` becomes a space and `%2B` becomes `+`.
  Command: `./mvnw -B -q -pl core -am test -Dtest='R47*,R48*,R43*,R46*' -Dsurefire.failIfNoSpecifiedTests=false`.
  Result: 4 tests, 1 failure: `[release of org.acme:lib:1.0+build (keys as the server read them:
  [/maven2/org/acme/lib/1.0 build/lib-1.0 build.pom])] Expecting value to be true but was false` (line 65).
  R43, R46 and R47 pass.
- **Impact:** the error is on the safe side: the snapshot is kept, nothing is deleted. Release-aware cleanup (D-106) still does
  nothing for `+` versions on S3/CloudFront release repositories. Design section 6 requires a request for exactly
  `<repo>/<groupPath>/<artifactId>/X/<artifactId>-X.pom`, and D-114's claim about the remaining sub-delims is wrong
  for this host. Quoting `+` as `%2B` names the same file on every other server, because RFC 3986 path decoding maps
  `%2B` to `+`.
- **Suggested task:** R48. Quote `+` as `%2B` in every segment, like `;`, and correct D-114's claim.

### F2 (minor): the self-publication now serves through Pages but ignores the README's Pages instruction (`nojekyll`)

- **What:** README line 211 tells Pages users to set `-Dgit-publisher.nojekyll=true` "so that Pages does not run Jekyll on
  the branch". With D-115 this project's own snapshots are served by Pages from `main`. However, neither the Maven deploy
  step (`.github/workflows/publish-maven-snapshots.yml:87-91`) nor `gradle-plugin/self-publish.init.gradle:33-36` enables
  `nojekyll`. The published branch has no `.nojekyll`: an anonymous shallow clone of `main` (tip b08cce7) has only
  `README.md` and `io/` at the root. Pages therefore runs Jekyll over every artifact on every push. Jekyll silently drops
  files and directories whose names start with `_` or `.`, and the Jekyll build time grows with the branch.
- **Evidence:** the file lines above. `git clone --depth 1 --branch main https://github.com/zenwave360/maven-snapshots.git`
  followed by `ls -a`: `.git README.md io`. Pages currently serves the metadata correctly: core build 34 and Gradle plugin
  build 6, identical to the branch, `Content-Type: application/xml`, `Cache-Control: max-age=600`, `X-Cache: MISS`.
  The dogfood therefore works today. It does not exercise the setup that the README documents.
- **Impact:** the dogfood consumer validates a Pages setup that the README advises against. A ZenWave artifact or
  classifier path that starts with `_` would disappear from the served site with no error. Hosting is the user's job (D-043),
  but here the user is this project, and it contradicts its own README.
- **Suggested task:** R49. Set `-Dgit-publisher.nojekyll=true` in the deploy step and `nojekyll = true` in
  `self-publish.init.gradle`, or record in D-115 why the branch is served with Jekyll.

## Checked and found solid

- R47/D-114: `;` becomes `%3B` in every segment (`a;b;c -> a%3Bb%3Bc`, `..; -> ..%3B`). `%` is always quoted by the URI
  constructor first, so an input `%3B` becomes `%253B`: there is no double decoding and no collision with a quoted `;`. Empty,
  `.`, `..`, `/`, `\`, NUL, DEL, U+0085 and TAB are doubt, with no request. `? # space` and U+2028 are quoted.
  `@ , = : ! $ & ' ( ) *` stay literal. I know of no common Maven server where these stay literal and resolve to a
  different existing POM: Tomcat/Jetty (Nexus, Artifactory, Reposilite on Jetty), nginx, Apache, Pages and Fastly map them
  as plain characters. A server that rejects `%3B` (Spring's StrictHttpFirewall, for example) answers 400. That is doubt,
  and the snapshot is kept. `+` on S3 is F1.
- D-115 publication: the Maven goal (`-Dgit-publisher.branch=main`), the init-script default and the read-back clone all
  use `main`. There is no other reference that publishes to or reads from `gh-pages` for this project. The plugin default
  stays `gh-pages` (design §2), and the tests use `gh-pages` only as a generic branch name. README, `readme/settings.gradle`
  and `ReadmeGradleSnippetsTest.SNAPSHOTS_SITE` use `https://www.zenwave360.io/maven-snapshots/` and agree.
- Consumer wait: I extracted the Maven wait step from the YAML and ran it with `sleep` removed against the live Pages URL
  (read-only GETs). With expected core 34 and plugin 3 it exits 0. With expected 35 and 99 it prints the served and
  expected builds and exits 1. The comparison is `-ge` on version-level build numbers of `io/github/ivangsa/...` only.
  A publication by another ZenWave project in between (another groupId, replayed under lease) changes neither those
  metadata files nor the outcome. A later Pages deployment of a newer tip still contains our files. A newer run of this
  workflow is serialized by `maven-snapshots-io.github.ivangsa` and passes `-ge`. Timeouts: 15 x 30 s plus 20 x 30 s of
  sleeps (17.5 min) inside a 20 min job, and `curl` has no `--max-time`. A Pages deployment that is still stale at the end
  therefore ends the job through its timeout, not through the diagnostic. The job still fails, so an older build never
  passes.
