## Findings

### F1 (minor) The action count is a proxy for "the record is last"; a count-preserving change still pushes after a failed participant

- **What:** D-103 makes `RecordSuccess` record only if `task.getActions().size()` equals the count stored when it was added, and states that
  "the check holds for any callback order". R32 asked for "a participant whose last action is not the record stays unrecorded". The count does
  not check that. A later `whenReady` that keeps the size equal still puts a failing action after the record, which records. The finalizer then pushes.
- **Evidence:** `gradle-plugin/src/test/java/io/github/ivangsa/gitpublisher/gradle/review/R33CountPreservingLateActionReviewTest.java`,
  5 cases, all fail with `Task :b:publishMavenPublicationToGitPublisherRepository FAILED` followed by `git-maven-publisher: pushed <sha>`:
  - remove-and-add (default, `--continue`, `--configuration-cache`): in a later `whenReady`, `t.actions.remove(1); t.doLast { throw ... }`. One earlier
    action is removed and one is added after the record.
  - wrap-last (default, `--continue`): `t.actions = [..., { task -> last.execute(task); throw ... } as Action]`. The record is wrapped and the
    wrapper fails after calling it.
- **Solid parts:** an action added in a later `whenReady` (R32), a `doFirst` or insertion before the record, an action added during the
  execution of another task (ad hoc probe: `jar.doLast { participant.doLast { throw } }`, nothing pushed, build fails), and `setActions`/`clear`
  that drop the record (the record never runs) all fail closed.
- **Impact:** low. It needs a build script or plugin that rewrites a publication task's action list after the graph is ready. But D-103's
  "any callback order" claim and R32's requirement do not hold.
- **Suggested task:** R33. Check that the last action is the record, not only the count. Add the record with
  `doLast("<unique name>", record)`. The action wrappers implement the public `org.gradle.api.Describable`: an ad hoc probe printed
  `Execute publish`, `Execute myNamed`, `Execute doLast {} action` for `task.getActions()`. When the record runs, it records only if the count
  matches and the last element of `task.getActions()` is `Describable` with the record's display name. Otherwise fail closed. Keep the
  configuration cache, and correct D-103.

### F2 (minor) README does not say that any late action fails the build; D-097 "Limit" is stale

- **What:** D-103 has a user-visible consequence: "a late action that succeeds also makes the build fail and nothing is pushed". README
  (Gradle section, lines 105-107) covers failed and skipped tasks only. It does not say that publication tasks must not get actions after the
  task graph is ready, or that such an action fails the build even when it succeeds. D-097's "Limit" bullet still says that an action
  added during execution "would still follow the record". Under D-103 that action fails closed. The D-097 correction note addresses only the
  "all added before the graph is ready" claim.
- **Evidence:** `grep -n -i "doLast\|whenReady\|task graph" README.md` finds nothing; `docs/decisions.md` D-097 Limit bullet.
- **Impact:** a user whose plugin adds a harmless `doLast` in `whenReady` gets a failed build with no documented reason (the warning only
  appears in the log).
- **Suggested task:** R34. Add a README sentence next to the skipped-task paragraph. Mark the D-097 Limit bullet as revised by D-103.

### F3 (minor) Composite builds: an included build's failed participant does not stop the root build's push

- **What:** each build of a composite has its own `Gradle` instance, recorded set, service and `gitPublisherPush`. With
  `includeBuild('inc')` and root `publish` depending on `gradle.includedBuild('inc').task(':publish')`, where both builds apply the plugin with
  the same remote, `inc`'s participant fails. `:inc:gitPublisherPush` refuses, but `:gitPublisherPush` pushes the root's publication. This
  happens with and without `--continue`. When both succeed, there are two pushes (the second after 2 attempts) instead of one.
- **Evidence:** ad hoc TestKit probe (removed): output `> Task :inc:publishMavenPublicationToGitPublisherRepository FAILED`,
  `> Task :inc:gitPublisherPush FAILED`, `> Task :gitPublisherPush`, `git-maven-publisher: pushed 9c3f44c... after 1 attempt(s)`. The branch
  holds `com/acme/app/...` only.
- **Impact:** one failed `gradle publish` invocation publishes part of its publications. Design section 2 and D-033 speak of "the build" and
  do not cover composite builds, so this is a gap in the design, not a departure from it. No review test is left, because the expected
  behaviour is not specified.
- **Suggested task:** R35. Decide whether a composite build is one publication or one per build (question for the maintainer). Record it in
  design section 2 and decisions, and state it in README. If it is one publication, make the push fail closed across included builds and add a test.

## Checked and found solid

- D-103 mechanism: one record per participant per build. The recorded set lives in `gradle.extensions.extraProperties`, which is new for each
  build, so TestKit runs that share a daemon (LateActionFailsClosed, the lifecycle tests) each get their own records. The count is taken
  right before `doLast`, as `size() + 1`. The count is serialized in the action, so the configuration-cache store and reuse runs pass
  (`ConfigurationCacheLifecycleTest` 28/28).
- Multiple projects that apply the plugin get no duplicate records (R32 test, 2 projects). Selecting one subproject and `--parallel` pass in
  the lifecycle tests. `PublishToMavenRepository` has no outputs and is not cacheable, so it is never UP-TO-DATE or FROM-CACHE. If a user makes
  it so, the record does not run, and D-098 fails the build.
- R29/D-098: skipped and unrecorded participants fail the build and name the task. `LateActionFailsClosedTest` shows that a harmless late
  action fails the build and nothing is pushed, in three schedules.
