## Findings

### F1 (minor): the release check still builds its URL by string concatenation; a `?` in a version or artifactId directory asks another resource

- **What:** R42 (D-109) closed the query and fragment of the repository URL, but `ReleaseCheck.exists` still appends
  `groupPath/artifactId/base/artifactId-base.pom` to the URL string without encoding (`ReleaseCheck.java`, `exists`: `URI.create(root + relative)`).
  `artifactId` and `base` come from directory names of the published tree (`VersionRetention.apply` / `releaseExists`), which are not
  validated: every directory that ends in `-SNAPSHOT` is a candidate. For a version directory `1.0?rc-SNAPSHOT` the URL is
  `<repo>/org/acme/lib/1.0?rc/lib-1.0?rc.pom`, so the request is `HEAD /maven2/org/acme/lib/1.0` with a query: not the POM of design section 6.
  A 200 with a non-HTML type there takes the version for released and deletes it. (`#` in a name gives an invalid URI, which answers "no"; `file:`
  repositories reject the query in `Path.of`, so only `https` is affected.)
- **Evidence:** `core/src/test/java/io/github/ivangsa/gitpublisher/review/R43ReleaseCheckPathSegmentReviewTest.java` fails:
  `[release of org.acme:lib:1.0?rc (requests: [/maven2/org/acme/lib/1.0])] Expecting value to be false but was true`.
- **Impact:** low likelihood (Maven's model validator bans `?` in versions; the tree can still hold any name Git allows, written by another tool or by hand),
  irreversible for the affected version. Same class as R42: the resource asked is not the one the design names.
- **Suggested task:** R43. Percent-encode each path segment (or answer "no" without a request for a segment with URI-reserved characters); the review
  test accepts either.

### F2 (minor): D-111 and the workflow comment misstate how GitHub Pages serves the snapshots branch

- **What:** the D-111 "Correction" says "`zenwave360.github.io/maven-snapshots/` answers 301 to [`www.zenwave.io`]" and that the branch "is not served by
  GitHub Pages"; the comment above "Check that the branch serves the Gradle plugin build just pushed" in `publish-maven-snapshots.yml` repeats it.
  Both are wrong: Pages redirects to `www.zenwave360.io`, which serves the branch. `www.zenwave.io` was a typo of the URL, not a Pages fault.
- **Evidence:** `curl -s -o /dev/null -w '%{http_code} %{content_type} -> %{redirect_url}'`:
  `https://zenwave360.github.io/maven-snapshots/io/github/ivangsa/git-maven-publisher-core/0.1.0-SNAPSHOT/maven-metadata.xml` gives
  `301 text/html -> https://www.zenwave360.io/maven-snapshots/...`. That URL gives `200 application/xml`, and so does the marker metadata
  `.../io.github.ivangsa.git-maven-publisher.gradle.plugin/0.1.0-SNAPSHOT/maven-metadata.xml`. `https://www.zenwave.io/maven-snapshots/...` gives `404 text/html`.
- **Impact:** the decision record, which later agents follow, gives a false reason for the URL choice. The raw.githubusercontent.com URL in the README and the
  consumer job is valid (both runs green), so nothing is broken.
- **Suggested task:** R44. Correct the D-111 note and the workflow comment. Whether the README snippet shows the Pages URL (`https://www.zenwave360.io/maven-snapshots/`)
  instead of the raw URL is the maintainer's choice. If it changes, change `src/test/resources/readme/settings.gradle` and `SNAPSHOTS_SITE` in
  `ReadmeGradleSnippetsTest` with it.

### F3 (minor): a failed Central upload hides Central's answer

- **What:** in `release-from-notes.yml`, the upload step uses `curl --fail-with-body --output deployment-id.txt`. On an HTTP error, curl writes the response
  body to `deployment-id.txt` and exits 22. The step stops under `bash -e` without printing that file, so the log shows only
  `curl: (22) The requested URL returned error: <status>`. Central's reason (bad request, namespace, authentication) is never shown. Also, the derived
  bearer `base64(user:token)` is not a registered secret, so GitHub does not mask it. Nothing prints it today, but no mask protects it.
- **Evidence:** file and step as cited. The curl semantics are documented (`--fail-with-body` writes the body to the output target).
- **Impact:** a failed first release is harder to diagnose. No secret leaks.
- **Suggested task:** R45. On a curl failure, print `deployment-id.txt` to stderr (the body has no credentials) before exiting non-zero. Add
  `echo "::add-mask::${bearer}"` before the curl call.
