## Findings

### F1 (minor): R43's allow-list rejects Maven-valid, URI-safe version names, so release-aware cleanup retains snapshots whose release POM exists

- **What:** `ReleaseCheck.plainSegment` accepts only `[A-Za-z0-9._+~-]+` (`ReleaseCheck.java:84-89`). It therefore
  returns doubt without a request for the valid Maven version `1.0@rc`. Maven's model validator defines the illegal
  version characters as only `\\/:\"<>|?*`; `@` is not among them, and it is a URI path character. For an old
  `1.0@rc-SNAPSHOT` directory with a release POM at
  `<repo>/org/acme/lib/1.0@rc/lib-1.0@rc.pom`, the code leaves the snapshot even though design section 6 requires
  release-aware cleanup to drop it.
- **Evidence:** the new failing review test
  `core/src/test/java/io/github/ivangsa/gitpublisher/review/R46ReleaseCheckValidMavenVersionReviewTest.java` asks a
  JDK HTTP server for exactly that POM. The focused Maven run fails it (1 test, 1 failure):
  `Expecting value to be true but was false` at line 56. The current early return at `ReleaseCheck.java:46-48` makes
  `released` false and sends no request, contradicting both assertions. Apache Maven's primary
  `DefaultModelValidator` declares `ILLEGAL_VERSION_CHARS = "\\/:\"<>|?*"`.
- **Impact:** a valid coordinate can accumulate obsolete snapshot versions forever when release-aware cleanup is
  enabled. This is fail-safe (it does not delete the wrong tree), but violates the configured cleanup contract.
- **Suggested task:** R46. Reject only characters that can alter a URI path (or percent-encode valid segments), and
  prove release cleanup for a Maven-valid `@` version while retaining R43's no-request rule for `?` and `#`.
