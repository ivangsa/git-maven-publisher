## Findings

### F1 (major): keepVersions deletes the version the publication just deployed, and still pushes

- **What:** `VersionRetention.apply` ranks every `-SNAPSHOT` directory, the touched ones included, by V-level `lastUpdated`
  (`VersionRetention.java`, the `byCount` block). Maven stamps V-level `lastUpdated` with the session start, not the deploy time (the behaviour D-025
  is built on). A long build of `2.0-SNAPSHOT` that started at 10:00 and deploys after a short `1.0-SNAPSHOT` build that started at 10:10 has the
  older `lastUpdated`. With `keepVersions=1` the publication of `2.0-SNAPSHOT` deletes `2.0-SNAPSHOT`, keeps the untouched `1.0-SNAPSHOT`, and pushes
  (`GitPublication.publish` reports `pushed=true`). This is an ordinary CI pattern (parallel branches, different build lengths), not clock skew.
- **Evidence:** `core/src/test/java/io/github/ivangsa/gitpublisher/review/R36KeepVersionsKeepsTheVersionJustPublishedReviewTest.java` fails:
  `Expecting HashSet ["1.0-SNAPSHOT"] to contain ["2.0-SNAPSHOT"]`.
- **Conflict:** brief "Snapshot semantics and retention" says keepVersions drops "old" `-SNAPSHOT` versions. Design §6 and D-106 (which names this case
  and rejects protecting the touched version without giving a reason) allow it. Design ranks higher, so this is a design defect to correct, not an
  implementation slip.
- **Impact:** a deploy that succeeds but whose artifact is not on the branch; consumers of the new version fail.
- **Suggested task:** R36. Never drop a version touched by this publication: touched versions count toward N, and only untouched versions,
  ranked by `lastUpdated`, are dropped. Update design §6 and D-106.

### F2 (major): release-aware cleanup cannot be switched on by users, and no task tracks that

- **What:** T48 asks for "a configurable release repo (default Central)". `RetentionPolicy.releaseRepository` exists only in the core API.
  `DeployMojo`/`PublisherParameters` (`new RetentionPolicy(keepSnapshots, keepVersions)`, `PublisherParameters.java:108`) and
  `GitPublisherService` (`GitPublisherService.java:198`) use the two-argument constructor, so the check is always off for Maven and Gradle users.
  D-106 records the gap as "a small follow-up for the adapter batches", but no task in docs/tasks.md covers it (B20 is T49 only).
  The default also changed from Central to off; D-106 records that, which is fine because decisions outrank tasks.
- **Evidence:** the file lines above; `grep -rn releaseRepository maven-plugin/src gradle-plugin/src` finds nothing.
- **Impact:** the T48 feature is unreachable from the user's side; the follow-up can be lost. T48's Done-when (a `file://` IT) passes, so T48 stays ticked.
- **Suggested task:** R38. Maven parameter `git-publisher.releaseRepository` and Gradle `releaseRepository` (URI, off by default; `central` or the
  Central URL accepted), passed to `RetentionPolicy`, included in the per-build consistency checks (`PublisherParameters` "differing",
  Gradle's shared-service parameter check), README entry, and one invoker IT plus one TestKit test against a `file://` release repository.

### F3 (minor): the https release check takes a redirect to an HTML page as "release exists", and the https branch has no test

- **What:** `releaseExists` builds the client with `followRedirects(NORMAL)` and returns `statusCode() == 200` for the final response.
  A repository that redirects unknown paths to an HTML login or landing page (repository managers behind SSO, captive proxies) answers every
  check with 200, and every untouched `-SNAPSHOT` version is deleted. Design §6: drop only when `.../X/<artifactId>-X.pom` exists; "any doubt keeps".
  The https path, the one the Central use case needs, has no test at all (`VersionRetentionTest` covers `file:` only). D-043's reason against
  an HTTP stand-in ("tested nothing of ours") does not hold here: the client is ours.
- **Evidence:** `core/src/test/java/io/github/ivangsa/gitpublisher/review/R37ReleaseCheckOverHttpsReviewTest.java` (JDK `HttpsServer`,
  throwaway key from the JDK's `keytool`). The controls pass: a direct 200 drops `1.5-SNAPSHOT`, a 500 keeps `1.6-SNAPSHOT`. The failing case:
  `302 -> /login (text/html, 200)` dropped `1.0-SNAPSHOT`.
- **Impact:** mass deletion of snapshot versions behind such a server; low likelihood against Central itself.
- **Suggested task:** R37. Treat a final response that is HTML (`Content-Type: text/html`) as doubt; keep following redirects so
  CDN redirects keep working. Do not change the review test's other cases.

### F4 (minor): release check cost and silent failure

- **What:** one new `HttpClient` and one sequential `HEAD` per untouched `-SNAPSHOT` version of each touched artifact, re-run on every retry
  attempt (`GitPublication.java` calls `Retention.apply` inside the attempt loop). With a blackholed network, each check waits up to the
  10 s connect timeout, so 30 old versions add about 5 minutes per attempt. During that time the lease window grows. The client sets no proxy
  (`HttpClient.newBuilder()` without `.proxy(ProxySelector.getDefault())`), so behind a corporate proxy every check fails. Every failure is
  silent ("any doubt keeps" with no log line), so users never learn that the feature does nothing.
- **Evidence:** `VersionRetention.releaseExists`; `GitPublication.publish` attempt loop.
- **Suggested task:** R39. Build one client per `Retention.apply` and use the default proxy selector. Remember the answers across attempts of one
  publication. Log one warning, without the URL's query, when a check fails for a reason other than 404.

### F5 (minor, documents): design §6 says retention never deletes non-timestamped files, but keepVersions does

- **What:** design §6 ends with "Non-timestamped files are never deleted by retention". The new keepVersions and release bullets delete whole version
  directories: the V-level `maven-metadata.xml`, its checksums, plain `lib-X-SNAPSHOT.jar` files and any user file inside the directory.
- **Suggested task:** R40. Restrict that sentence to build retention (`keepSnapshots`) and state that keepVersions and release cleanup remove the
  whole directory.

## Checked and found solid

- Retention runs again on every attempt after `replayOntoRemote`, on the fresh remote tree plus our recorded changes. Drops are never replayed
  from a stale tree. `ChangeRecorder` records before retention, so drops never enter `ours`.
- A-level rewrite: dropped names leave `<versions>`, `<latest>` moves only when it named a dropped version, and checksums are regenerated for configured
  plus already-present algorithms (`ChecksumWriter.write`). An untouched A-level file stays byte-identical. `IntegrityCheck` still runs before the commit.
- Only `*-SNAPSHOT` child directories of touched artifacts are candidates. Release directories, loose files, nested groupId directories and
  untouched artifacts stay.
- `RetentionPolicy` rejects other schemes and userinfo, and its messages do not echo the URI. Errors, non-200 statuses and an unreachable `file:` path keep
  the version (R37 controls: 500 kept, missing `file:` path kept by `VersionRetentionTest`).
- Same-`groupId:artifactId` concurrency stays excluded by D-032. Distinct-coordinate publishers cannot share a dropped directory.
