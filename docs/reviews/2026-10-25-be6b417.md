## Findings

### F1 — Major: a project with two bound executions pushes before the second execution succeeds (R25)

**What:** `ReactorTransaction.checkIn` counts project identities, and sets `completed` as soon as every project has
checked in once (`maven-plugin/src/main/java/io/github/ivangsa/gitpublisher/maven/ReactorTransaction.java:93–96`).
With two `deploy` executions in a single project, the first execution therefore publishes immediately. The second
execution may fail afterwards, contrary to design §2/D-034's guarantee for every participating execution.

**Evidence:** the real Maven invoker project `review-repeated-execution` binds `first` and `second-fails` to deploy.
The first has valid settings; the second configures `checksumAlgorithms=INVALID`. Its output contains, in order:

```text
--- git-maven-publisher:0.1.0-SNAPSHOT:deploy (first) @ repeated ---
Published 1 project(s) in one commit ... (1 attempt(s))
--- git-maven-publisher:0.1.0-SNAPSHOT:deploy (second-fails) @ repeated ---
BUILD FAILURE
unknown checksum algorithm 'INVALID'
```

`R25RepeatedExecutionReview.verify` then fails: `[branch gh-pages] Expecting an empty Optional but was containing value`.
The fixture resets its own remote refs before each run, so this is a publication made by the failing invocation.

**Impact:** a failed participating execution can leave artifacts published. This is a participating execution of the
same plugin, not the documented exception for a trailing non-participating module.

**Suggested task R25:** account for all participating executions, or reject multiple bindings before any checkout/push.
Keep the existing skipped-module, parallel, failure and trailing-non-participant guarantees. T26 fails verification.

### F2 — Major: retention searches for the version/timestamp inside arbitrary filename prefixes (R23)

**What:** `Retention.java:80–88` searches with `Matcher.find()` for `<baseVersion>-<timestamp>-<number>` anywhere
in the filename, without checking the full artifactId prefix. It can parse part of a legal artifactId as the build id,
or delete a file whose name is unrelated to that coordinate's timestamped artifacts.

**Evidence:** both `R23RetentionFilenameBoundaryTest` tests fail against real Resolver output:

- Three native deploys of `org.acme:lib-1.0-20200101.010101-99:1.0-SNAPSHOT`, followed by `keepSnapshots=1`, leave
  all six main/source jars instead of two. Every filename is incorrectly grouped under the `99` embedded in artifactId.
- For ordinary `org.acme:lib:1.0-SNAPSHOT`, retention deletes the unrelated
  `notes-1.0-20200101.010101-0.txt` file. It is not a timestamped artifact of `lib`.

Both source repositories pass `MetadataAssertions` before retention. The first regression reports
`Expected size: 2 but was: 6`; the second reports the notes path no longer exists.

**Impact:** the configured retention limit can be silently ineffective, and unrelated files can be removed.

**Suggested task R23:** recognize the canonical timestamped filename after the complete artifactId and base version;
preserve unrelated filenames and retain exactly the configured number of native builds. T16 fails verification.

### F3 — Minor: the integrity gate accepts metadata the Maven oracle rejects (R24)

**What:** the StAX tree accepts duplicate known fields, and `XmlNode.child`/`MetadataModel.artifactId` silently use
the first. `IntegrityCheck` treats this as a successful parse. Design §5 requires metadata that parses with Maven's reader.

**Evidence:** `R24IntegrityOracleParsingTest` deploys a valid Resolver tree, duplicates A-level `<artifactId>`, and
regenerates the checksums. The real `maven-repository-metadata` reader used by `MetadataAssertions` rejects the XML.
`IntegrityCheck.verify` returns normally; the regression fails with `Expecting code to raise a throwable`.

**Impact:** corrupt existing metadata for a coordinate can pass the pre-push gate when another coordinate is published.
The production gate and the independent oracle disagree about repository validity.

**Suggested task R24:** reject duplicate known metadata fields without adding Maven runtime dependencies to core;
retain the existing unknown-element preservation and namespace tests. T17 fails verification.
