## Findings

### F1 (major) A participant that fails after its publish action is pushed

- **What:** `GitMavenPublisherPlugin` records success with `task.doLast(new RecordSuccess(...))` inside `configureEach`
  (`GitMavenPublisherPlugin.java:98-105`). Actions added to the same task later (a build script's `doLast`, another plugin) run after
  that record. If one of them fails, the task is FAILED but already recorded, and `gitPublisherPush` (a finalizer, which Gradle runs
  after a failed finalized task) pushes. Design section 2 (D-033): "A failed publication prevents push"; design section 2 push guard.
- **Evidence:** `gradle-plugin/src/test/java/io/github/ivangsa/gitpublisher/gradle/review/R26LateParticipantFailureReviewTest.java`
  fails for both schedules (default and `--continue`). Output: `> Task :b:publishMavenPublicationToGitPublisherRepository FAILED`
  followed by `git-maven-publisher: pushed 32af29d... after 1 attempt(s)`, then `BUILD FAILED`.
- **Impact:** a build that failed in a participant publishes. The T36 tests miss it because every failure they inject is a `doFirst`.
- **Suggested task:** R26. Record the outcome so that no action of the participant can run after it (for example, a task-completion check
  that sees the task's final state, or recording in an action registered after all others and rejecting later additions), keep the
  configuration cache. Restore T36.

### F2 (major) The release job publishes the Gradle plugin before core is on Central

- **What:** `.github/workflows/release-from-notes.yml:47-86`, job `gradle-plugin`, `needs: release`, then runs `publishPlugins`. The comment says
  "Runs after the Maven release, so core is already on Central". It is not: the Maven release uploads with `autoPublish` false
  (`pom.xml:323`, and `release-maven.yml` job "Build and publish Maven Central deployment (autoPublish=false)"), so the deployment waits in
  the Central portal until the maintainer publishes or drops it (T32b: "publish or drop it").
- **Impact:** the Plugin Portal gets version X whose POM depends on `git-maven-publisher-core:X`, which is not resolvable until (and unless)
  the maintainer publishes the Central deployment. A dropped deployment leaves a plugin version on the portal that can never resolve, and
  portal versions cannot be re-published under the same number. D-083 ("publishes the Gradle plugin from the release caller job after
  the Maven release") and D-095 do not address the manual Central step.
- **Suggested task:** R27. Publish the plugin only once core X is resolvable from Central: for example, a separate maintainer-dispatched
  workflow (or job input) after the Central publish, or a step that checks `https://repo.maven.apache.org/maven2/io/github/ivangsa/git-maven-publisher-core/X/`
  and fails before `publishPlugins` when it is absent. Record it in decisions. T45 stays `[?]` (Q12).

### F3 (minor) `ReadmeGradleSnippetsTest` fails on a fresh Windows checkout

- **What:** `ReadmeGradleSnippetsTest.java:55` compares `Files.readString(SETUP)` raw with the README block, which `fencedBlocks`
  normalizes from CRLF to LF. With `core.autocrlf=true` (Git for Windows default) `src/test/resources/readme/build.gradle` is checked
  out with CRLF (`file` reports "with CRLF line terminators"), so the strings differ only in line endings. `.gitattributes` does not pin
  that file. The main checkout predates the file and has LF, so the implementer's build passed.
- **Evidence:** the failure above in the worktree build; `assertEquals` shows identical text.
- **Impact:** the full build is red on any fresh Windows clone (AGENTS.md: Windows through Git Bash is a supported environment). T44's
  "Done when" (snippets copied from passing TestKit builds) does not hold there.
- **Suggested task:** R28. Normalize both sides (or pin the resource with `eol=lf` in `.gitattributes`). The test is provably wrong on
  CRLF checkouts; record the edit in decisions. Restore T44.

### F4 (minor) A skipped participant makes a green build that publishes nothing

- **What:** `GitPublisherService.publishIfComplete` (lines 142-152) logs a warning and returns when a participant was not recorded. A
  participant skipped by Gradle (`onlyIf { false }`, `enabled = false`) never records, so the push is refused and the build reports SUCCESS.
  Design section 2 asks for "no push, with a log line"; D-086 calls it a known limit. No test covers it (`grep onlyIf` in
  `gradle-plugin/src/test` finds nothing), so the documented behaviour is unverified.
- **Impact:** a CI job is green while no snapshot was published; the Maven adapter treats a skipped participant as non-participating and
  publishes the rest (design section 2, Maven). The difference is not in the README.
- **Suggested task:** R29. A TestKit test for a skipped participant that pins the chosen behaviour, and either fail the build (preferred:
  a refused push is not success) or state the limit in the README.
