## Findings

### Critical

**F1. Retention (§6) deletes the build that was just published and that the metadata references. MetadataAssertions does not notice.** (R01)
- *What:* Maven stamps snapshots with the session **start** time (`maven.startTime`, set by maven-core 3.10.0
  `DefaultRepositorySystemSessionFactory` and read by `RemoteSnapshotMetadataGenerator`), not the deploy time. A build
  that started earlier and deploys later gets an **older timestamp and a higher build number**, and Maven's metadata points
  at it. §6 orders builds by `(timestamp, buildNumber)`, so it sees that build as the oldest one.
- *Evidence:* scratch run with real Resolver plus §6 applied as written (B started 1 min ago and deployed first; A started 10 min ago and deployed last; keepSnapshots=1):
  ```
  builds newest first by (timestamp, buildNumber): [20261023.141052-1, 20261023.140152-2]
  retention keepSnapshots=1 deletes: [20261023.140152-2]
  <snapshot><timestamp>20261023.140152</timestamp><buildNumber>2</buildNumber></snapshot>  <snapshotVersions></snapshotVersions>
  MetadataAssertions violations: []
  clean Maven consumer resolves org.acme:lib:1.0-SNAPSHOT: false
  Could not find artifact org.acme:lib:jar:1.0-20261023.140152-2 in pages
  ```
  This is a plain sequential case: no concurrency, no merge. Two CI runs where the first one is slower are enough.
  `MetadataAssertions` (`MetadataAssertions.java:118-137`) does not check `<snapshot>`, so IntegrityCheck (T17 must
  agree with it) would push this tree. `R01SnapshotElementInvariantTest` reproduces the end state.
- *Impact:* the snapshot that was just published becomes unresolvable for every consumer, and it is deleted. Silent data loss.
- *Also affected:* §5 "per key the entry with greater `updated` wins" and "`snapshot` timestamp from the newest entry,
  `buildNumber` = max": `updated` comes from the start time too, so the merge can choose a different build than Maven, or
  produce a `<snapshot>` timestamp/buildNumber pair that names no build at all.
- *Suggested task:* R01. Change design §5/§6 so that build order is decided by build number (tie-break by timestamp),
  not by timestamp. Add an invariant to §5 and `MetadataAssertions`: `<snapshot>` (timestamp, buildNumber) must name a
  build that has files in the directory. Record the decision.

### Major

**F2. The Resolver oracle does not deploy "exactly like mvn deploy".** (R02)
- *What:* `ResolverDeployer` never sets `maven.startTime`, so each deploy is stamped with the wall clock at deploy time.
  No harness scenario can produce the out-of-order timestamps behind F1. Sequential reference, concurrency harness and
  every Phase 1 test would pass on the §6 bug.
- *Evidence:* `ResolverDeployer.java:74-79` (no `maven.startTime`); `R02ResolverDeployerSessionStartTimeTest`
  (two deploys in one deployer, 1.5 s apart, get different timestamps; in Maven one session has one timestamp).
- *Suggested task:* R02. One deployer behaves as one Maven session (start time fixed when the session is created). Add a way
  to give a start time, so tests can model "started earlier, deployed later". Use it in
  `ConcurrentPublishScenario` (start time taken at the barrier, before checkout).

**F3. The `refs/publisher/tree` lease (§4.5, D-020) blocks publishing permanently once the branch is pushed without it, and leaves partial pushes.** (R03)
- *What:* the expected old id of the tree ref is "the tree of `expectedSha`". When the branch exists but the tree ref does
  not, or points elsewhere, that lease can never succeed. This happens when the branch was created by hand or by a Pages
  setup, or when anyone pushes the branch with plain `git`. The push is not atomic, so the branch update succeeds anyway.
- *Evidence:* scratch run with JGit 7.8.0 over `file://` (branch created by a normal commit, no tree ref):
  ```
  refs/heads/gh-pages -> OK
  refs/publisher/tree -> REJECTED_REMOTE_CHANGED
  branch moved to our commit: true
  tree ref on remote: null
  ```
  With §4.6 ("REJECTED_REMOTE_CHANGED → back-off, re-fetch, replay, retry") every attempt rewrites the branch and is
  rejected again, until `maxAttempts`. The publish then reports failure even though the branch was already updated, and
  every later publish fails the same way.
- *Suggested task:* R03 (design only, before T20). The tree ref is an optimization, not a lease. Push it forced with no
  expected old id, or with the id fetched for it, and ignore its status. Only the branch status decides OK or retry.
  Consider `setAtomic(true)` where the server supports it. Add a T20 "Done when": the branch exists without the tree ref,
  and the publish succeeds in one attempt.

**F4. Same-snapshot concurrency: identical file names and the wrong reference order.** (R04)
- *What (a):* two builds of the same `-SNAPSHOT` that check out the same tip and start in the same second produce
  **identical file names** with different content. Scratch run, two checkouts of one base, start times 400 ms apart:
  `x: [lib-1.0-20261023.140845-1.jar]`, `y: [lib-1.0-20261023.140845-1.jar]`. §7 calls this "should be impossible with
  timestamped names" and throws `PublishException`. It is possible, for example in a CI matrix publishing the same version.
- *What (b):* the harness cannot see it. `ConcurrentPublishScenario` deploys byte-identical content for equal coordinates
  (`ResolverDeployer.deployJavaProject`), and `lostFiles()` matches by path plus content
  (`ConcurrentPublishScenario.java:163-174`). Two publications that collapse into one build count as "nothing lost". In
  `mixedSteps(8)`, four threads publish `shared:1.0-SNAPSHOT` from one barrier, so T22 will hit this and pass.
- *What (c):* `assertMatchesSequentialReference` replays `deployOrder()`, the order in which deploys **finished**
  (`ConcurrentPublishScenario.java:139`). With the §5 rules, the A-level `<versions>` of a correct publisher follow **push**
  order ("remote order, then ours appended"). Deploy order and push order differ whenever a later deploy wins the push, so
  T22/T23 would flag a correct publisher. Example: T1 `shared:1.0` deploys first, T2 `shared:2.0` deploys second and
  pushes first. Actual `[2.0, 1.0]`, reference `[1.0, 2.0]`. It passes today only because `globalLock()` makes both
  orders equal.
- *Suggested task:* R04. In the design, decide what replay does when its build number collides with the remote. The
  suggestion: renumber our build to remote max + 1, renaming files and checksums and rewriting our metadata entries.
  That keeps build numbers unique and in push order, as a sequential `mvn deploy` would, and fits F1. In the harness,
  give each publication unique content, record the push order, not the deploy order, and replay that order in
  `assertMatchesSequentialReference`.

**F5. LeakScanner misses the token in an HTTP basic auth header.** (R05)
- *What:* JGit receives `UsernamePasswordCredentialsProvider(x-access-token, token)`. Any debug or wire log of the
  request contains `Authorization: Basic base64(x-access-token:<token>)`. `scanText` only searches for the raw canary
  (`LeakScanner.java:48-54`).
- *Evidence:* `R05LeakScannerBasicAuthTest`.
- *Suggested task:* R05. Also detect the Base64 forms (of `user:canary` for the configured usernames, and of the canary at
  each of the three alignments) and the URL-encoded canary, in text, file contents and Git config.

### Minor

**F6. TreeNormalizer leaves timestamps inside `.module` files.** (R06) Gradle writes timestamped file names into
`.module` (`variants[].files[].url`). The contents are compared raw (`TreeNormalizer.java:68-77`), so the Gradle
differential T41 can never pass, and checksums of `.module` files will differ too. Evidence:
`R06TreeNormalizerModuleFileTest`. Suggested task: R06. Normalize `.module` contents the way metadata is normalized, and
treat their checksum files as metadata checksums are treated.

**F7. "Every `<version>` has a directory" accepts an empty directory.** (R07) Git does not store empty directories, so
a tree that passes in `repo/` fails on the pushed branch. Retention by `keepVersions` (T47) is exactly the code that
empties version directories. Evidence: `MetadataAssertions.java:150`, `R07EmptyVersionDirectoryTest`. Suggested task:
R07. Require at least one regular file below the version directory.

**F8. Profile `e2e` replaces the failsafe includes.** `test-fixtures/pom.xml:109-111` sets
`<includes>**/*E2E.java</includes>`, which drops the default `**/*IT.java`. CI always runs `-Pe2e`, so any future `*IT`
in `test-fixtures` would never run in CI. No `*IT` exists yet. Also, the CI zero-test guard (`ci.yml`, last step) sums
`tests=`, which includes skipped tests: an E2E that becomes `disabledWithoutDocker` would still count as executed. Fold
both into R05's batch, or fix together with T22. Use a separate failsafe execution for E2E, and count
`tests - skipped`.
