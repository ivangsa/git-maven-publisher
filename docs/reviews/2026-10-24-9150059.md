## Findings

### Major

**F1. Rewriting namespaced metadata drops attribute prefixes; Maven's strict reader then rejects the file. (R11)**

- **What:** `XmlNode.read` parses with `IS_NAMESPACE_AWARE=false` and stores attributes under
  `reader.getAttributeLocalName(i)` (`src/main/java/io/github/ivangsa/gitpublisher/XmlNode.java:112,125`). Element names keep
  their prefix, attribute names lose it: `xmlns:xsi` becomes `xsi`, `xsi:schemaLocation` becomes `schemaLocation`, and
  `<ext:foo xmlns:ext="urn:x">` becomes `<ext:foo ext="urn:x">` (unbound prefix, not namespace-well-formed).
- **Evidence:** `src/test/java/io/github/ivangsa/gitpublisher/review/R11NamespacedMetadataRewriteTest.java`. A real
  Resolver tree whose V-level metadata carries the standard `xmlns`/`xmlns:xsi`/`xsi:schemaLocation` root passes
  `MetadataAssertions` (Maven's `MetadataXpp3Reader`, strict). After `Retention.apply(keep=1)` drops the javadoc entry and
  rewrites the file, `MetadataAssertions` reports
  `does not parse with maven-repository-metadata: Unknown attribute 'schemaLocation' for tag 'metadata'`.
  The second case shows the round trip writes `xsi="..."` and `schemaLocation="..."`.
- **Impact:** retention turns metadata that Maven reads strictly into metadata it rejects, which breaks the design §5
  invariant "parses with the oracle parser". `IntegrityCheck` parses with the same `XmlNode`, so it does not catch it, and
  T17's agreement with `MetadataAssertions` fails on this input. D-048 says "unknown elements and attributes stay where
  they were", which is not true for prefixed attributes. The golden round-trip test (T13) misses it because no golden
  file has namespace declarations. Writers that emit them (Maven 4's StAX writer is the obvious candidate for T29) hit this
  on every retention rewrite.
- **Suggested task:** R11. Keep qualified attribute names (prefix + local name, namespace declarations included), or parse
  namespace-aware and write the declarations back. Add a namespaced golden-style case to the round-trip test.

**F2. The core config has no checksum algorithms, but retention and integrity need them. (R12)**

- **What:** design §5 says checksums of rewritten metadata are regenerated for the algorithms present "plus the configured
  ones", and every metadata file must have checksum files "for the configured algorithms". `Retention.apply(..., checksums)`
  and `IntegrityCheck.verify(root, required)` take that set as an argument (`Retention.java:59`, `IntegrityCheck.java:49`).
  `PublishConfig` (design §3 and `PublishConfig.java`) has no field for it, so `GitPublisher.publish()` (T20/T21) has no
  way to get the configured set. Design §2 has the Maven `checksumAlgorithms` parameter only as "passed to Resolver".
- **Evidence:** the record components in `src/main/java/io/github/ivangsa/gitpublisher/PublishConfig.java` and
  `docs/design.md` §3 (line 109).
- **Impact:** T20/T21 will have to invent the plumbing, or call `IntegrityCheck` with an empty set, which only checks "at
  least one checksum file" and so weakens the §5 invariant. The design also lists `PublishConfig` without `nojekyll`
  (D-047 added it in code), so design §3 has already drifted from the code.
- **Suggested task:** R12. Design §3 + decision: add `checksumAlgorithms` (default SHA-1, MD5; Gradle: what Gradle writes)
  and `nojekyll` to `PublishConfig`; validate the set is not empty; unit tests.

### Minor

**F3. A `file` URL with credentials in a registry-based authority passes validation. (R13)**

- **What:** `PublishConfig.validateRepository` relies on `URI.getRawUserInfo()` (`PublishConfig.java:97`), which is null
  when `java.net.URI` cannot parse the authority as server-based (for example a host with `_`). `https` is caught by the
  "must have a host" check; `file` has no such check.
- **Evidence:** `src/test/java/io/github/ivangsa/gitpublisher/review/R13RegistryAuthorityUserInfoTest.java`:
  `file://user:secret@my_host/repo.git` and `file://secret@my_host/repo.git` are accepted.
- **Impact:** small (`file` remotes are local), but design §8 says URLs with userinfo are rejected and the URL may later
  appear in logs or diagnostics.
- **Suggested task:** R13. Reject any `@` in the raw authority (and in the scheme-specific part of opaque URIs); messages
  still must not echo the URL.

**F4. Documents still name removed components.**

- `docs/tasks.md` T48 "Done when: IT against a `PagesServer`-hosted fake release repo": `PagesServer` was removed (T56, D-043).
- `docs/decisions.md` D-038 (lines 369–370) still lists "consumers over a local HTTP server" and "negative integrity and leak
  tests", contradicting D-043 and D-045, and is not marked "Revised by". Newest-wins resolves it, but the entry should say so.
- Design §3 `PublishConfig` lacks `nojekyll` (see F2).
- **Suggested task:** folded into R12 (documents only).

**F5. `assertBothPublished` passes without any interleaving.**

- **What:** `InterleavedPublishScenario.Outcome.assertBothPublished` (`InterleavedPublishScenario.java:278`) does not check
  `interleaved()`; a publisher that never calls `Publication.checkedOut()` runs A then B and passes (the `globalLock`
  self-test relies on it).
- **Impact:** T21/T23 tests built on it can pass without a lease failure ever happening, if the adapter forgets the
  interleaving point. The "Done when" of T21 and T23 requires forced lease failures.
- **Suggested task:** R14. Add `assertInterleavedAndBothPublished` (or a flag) that requires `interleaved()`, and use it in
  T21/T23; keep the lock path for the reference publisher.
