## Findings

### Major

**F1. Since the push became atomic, a rejected tree hint blocks every publication.**
- What: design §4 step 3.vi, D-027 and the T20 "Done when" all say a rejected `refs/publisher/tree` never fails or retries a
  publish; only the branch status decides. R18 (D-060) made the branch and hint one atomic push. A remote that refuses the hint
  ref now refuses the whole push, and `GitRemote.push` (`GitRemote.java:129`) reports it as a permanent rejection with the hint
  "the branch must allow force pushes", which is wrong. Every later publication to that remote fails the same way, because the
  hint is pushed every time. Design §4 now contradicts itself: step 3.v says "atomic", step 3.vi still says "whatever the status
  of the tree ref (it may be missing, stale or rejected ...)". D-060 says "revises D-027" but leaves this case open.
- Evidence: `src/test/java/io/github/ivangsa/gitpublisher/review/R19RejectedTreeHintTest.java`, using a real JGit receive-pack
  over `file://` that cannot lock `refs/publisher/tree` (a stale `refs/publisher/tree.lock` on the server):
  `PublishException: ... the remote rejected the push to refs/heads/gh-pages: REJECTED_OTHER_REASON (transaction aborted); the
  branch must allow force pushes`. The sanity test in the same class shows that the same refusal in a non-atomic push leaves
  the branch `OK` (D-027's premise).
- Impact: any host or hook that refuses non-branch refs (namespace policies, refs that point at trees, a stale lock on a
  self-hosted bare repo) makes the plugin unusable against it, with a diagnostic that sends the user to branch protection.
  Before R18 the same remote worked.
- Suggested task: R19. Keep "a failed publication moves no ref" (R18) without making the hint able to fail the branch. For
  example: when an atomic push is rejected and the branch was not refused for the lease, push again with the branch only
  (lease intact) and log that the hint was refused. Or update design §4.6, D-027 and T20 with a decision that accepts this
  failure mode. Either way, `R19RejectedTreeHintTest` is the specification. Restore T20 after the full build passes.

### Minor

**F2. The atomic fallback is chosen by a word in the URL.**
- What: `GitRemote.push` (`GitRemote.java:107`) falls back to a non-atomic, hint-less push when the `TransportException`
  message contains "atomic". That message starts with the repository URL. This is the mistake R15 removed from the auth
  classification. On a repository named for example `atomic-snapshots`, a transient push failure (503, connection reset) is
  not retried as a transport error. It is pushed again at once, non-atomically and without the hint. A 401 at push makes two
  authenticated pushes instead of one.
- Evidence: `src/test/java/io/github/ivangsa/gitpublisher/review/R20AtomicFallbackTest.java` against a JGit `GitServlet` over
  HTTPS whose first receive-pack POST answers 503:
  `aTransientPushFailureIsRetriedWhateverTheRepositoryIsCalled` fails with attempts expected 2, was 1 (and no hint). The same
  test with the path `/acme/plain-snapshots.git` passes (checked by hand). The same class closes D-060's "fallback has no
  test" gap: `aServerWithoutAtomicPushGetsTheBranchWithoutTheHint`, against an `InMemoryRepository` with atomic transactions
  off, passes. The real fallback works.
- Impact: the retry and back-off contract (design §4 3.vi) is skipped for these repository names, and the hint is lost (the
  next push resends the whole tree). Nothing wrong is published.
- Suggested task: R20. Decide on JGit's own condition: the advertised capabilities (`atomic` missing), or the
  `JGitText.atomicPushNotSupported` text with the URL removed, as in `isFatal`.
